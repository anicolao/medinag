# Watch responses followed by more alerts — 2026-11-12

## Evidence

Alex reported first seeing the 13:00 dose on Watch at 13:03, responding, and
receiving further alerts including 13:27 despite responding again.

Read-only production inspection found that the 13:00 occurrence was still
`pending`, with zero snoozes and no completion timestamp. Its 13:15 update was
the unanswered-dose escalation, not a patient response. The phone's latest
coverage record was at 10:09 local time, build 16, with 55 pending requests.
That coverage record proves registration inventory only, not delivery or taps.
No production dose was manually changed during this investigation.

The paired phone/Watch were listed by CoreDevice, but connections to retrieve
their journals failed (phone transport timeout; Watch pairing rejection).
Consequently, we cannot identify exactly which notification source or callback
path Alex encountered, or explain the late initial alert from these records.

## Defects found and addressed

- Watch notification handling lived in a SwiftUI `StateObject`, rather than a
  launch-time application delegate. Notification-only launches must establish
  their handler before launch completes, without requiring a rendered scene.
- The iPhone's WatchConnectivity receiver and response-outbox processing also
  depended on a SwiftUI-owned view model. The application delegate now owns the
  same model used by the UI and starts it for background launches as well.
- Watch commands awaited the entire phone initialization task, including remote
  Auth/Firestore operations. They now await local cache/identity restoration,
  allowing cancellation and durable local acceptance before network completion.
- Watch activation could spend its short background slot refreshing before
  queuing the response. Queue the response first; keep the notification callback
  alive for actual WCSession activation, bounded by a two-second product timeout.
- A refresh command assigned raw fetched events directly, bypassing local
  responses/policy. It now preserves response progress and applies the outbox.
- Newer transport timestamps could contain older response data. Completion is
  terminal for an unchanged occurrence; snooze counts do not decrease. An ACK
  with an unanswered snapshot no longer clears the durable Watch response.
- A later completion can replace an unsynchronized snooze. An older snooze
  version on a notification must not invalidate completion of the same active
  occurrence. New occurrences and changed schedule times remain distinct.
- Persist the phone's updated/confirmed cache before removing its durable intent.
  At the serialized OS-queue boundary, retain bounded durable response progress
  separately from the synchronization outbox, so an old in-flight refresh cannot
  reinstall alerts even after restart and acknowledgement.
- Log cancellation requests and verify obsolete requests are actually absent
  from OS pending inventory. Log explicit rejected-action reasons and actual
  phone command receipt to distinguish ignored actions from transport delays.

## Initial-alert race reproduced during final validation

The connected rerun failed to show the initial OS notification. Its actual
on-device journal showed registration of that initial request followed by its
cancellation when a refresh crossed the logical deadline, before iOS had consumed
the pending request. Calendar triggers have second precision; with the accelerated
clock, the rounded physical deadline could still be in the future at that point.
The same cancellation race exists in production when an OS-owned due request
has not yet been presented. This can leave the first repeat as the first visible
alert, consistent with the reported 13:03 observation, though it is not a device
trace proving exactly what happened at 13:00 on Alex's Watch.

Refresh now retains an actual pending, due request for the same unanswered
occurrence and response version. Completion, snooze, or the next dose invalidates
it normally. These are **existing OS requests**, not recreated past requests or
fabricated delivery. Retained requests reserve queue capacity, and any still-future
calendar deadline is included in inventory verification. Tests cover crossing
the initial deadline, an exact repeat boundary, completion, snooze and retirement.

Build 17 contains the response fixes but predates this newly found race fix.
Build 18 is the intended combined test candidate; do not treat 17 as the complete
fix for this incident.

Apple requires [notification delegates before launch completes](https://developer.apple.com/documentation/UserNotifications/UNUserNotificationCenterDelegate)
and describes [notification actions launching apps in the background](https://developer.apple.com/documentation/usernotifications/handling-notifications-and-notification-related-actions).
These code defects can cause lost responses or resurrected alerts; without the
device journals, they are not proof of the precise path taken by Alex's taps.
